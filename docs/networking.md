# 双端通信：现状与公网化方案

---

# 一、现在是怎么通信的

## 1. 传输层

一个端口干两件事。`server/index.js` 里 Express 和 `ws` 挂在**同一个 `http.Server`** 上：

```js
const server = http.createServer(app);        // 静态资源：/、/js/*、/shared/*、/vendor/three/*
const wss = new WebSocketServer({ server });  // 同端口的 WebSocket 升级
```

所以客户端不需要知道第二个端口，直接 `new WebSocket('ws://' + location.host)` 就连上了。

**载荷是 JSON 文本**，没有二进制编码、没有压缩。每条消息都是一个对象，靠 `t` 字段区分类型
（`shared/protocol.js` 里定义，服务端和浏览器共用同一份常量）。

## 2. 三个阶段

```
浏览器                                    服务器
  │  ── HTTP GET / ────────────────────►  │  静态页面
  │  ── WebSocket Upgrade ─────────────►  │
  │  ◄──────────────────── welcome ────   │  配置 + 昵称历史 + 占用列表 + 你的 IP
  │                                       │  （此时还没有蛇，也不会收到 state）
  │  ── join {nickname, skin} ─────────►  │  校验昵称占用
  │  ◄──────────────── joined {id} ────   │  创建蛇，此后开始收 state
  │      或 ◄───────── reject {reason}    │  昵称被占，附带建议名
  │                                       │
  │  ◄──────────────── state ──────────   │  30 包/秒，每包 2 帧位置
  │  ── input {dir, sprint} ───────────►  │  只在按键变化时发
  │  ── jump ──────────────────────────►  │  按一次发一次
  │  ── ping {c} ──────────────────────►  │  1 秒一次
  │  ◄──────────────── pong {c} ───────   │  客户端据此算 RTT
```

**关键点：welcome 在 join 之前**。配置（地图大小、珠子半径、颜色表、插值延迟…）是服务器下发的，
不是客户端硬编码的——改 `config/game.config.js` 重启服务器，所有客户端自动跟上，不用改前端。

## 3. 消息清单

### 客户端 → 服务器（`C2S`）

| 类型 | 内容 | 频率 |
|---|---|---|
| `join` | `{nickname, skin}` | 一次 |
| `input` | `{dir: 弧度, sprint: bool}` | **事件驱动**：只在方向键/Shift 状态变化时发，不是每帧 |
| `jump` | `{}` | 按一次发一次 |
| `ping` | `{c: performance.now()}` | 1 Hz |

输入是"意图"而不是"位置"：客户端只告诉服务器"我想朝这个角度走"，蛇实际怎么转、能不能转过来，
由服务器按 `turnRate`（冲刺时再乘 `sprintTurnFactor`）算。**客户端发不出任何能直接改变位置的东西。**

按住 W 不动时一个包都不会发——这是 `client/js/input.js` 里 `evaluate()` 的比较逻辑：
方向角和 sprint 都没变就直接 return。稳态下上行流量基本只有每秒一个 ping。

### 服务器 → 客户端（`S2C`）

| 类型 | 内容 |
|---|---|
| `welcome` | `{config, skinLabels, nicknames[], taken[], defaultNickname, ip}` |
| `joined` | `{id, nickname, skin, trophies}` |
| `reject` | `{reason, suggestion, taken[]}` |
| `state` | `{f: [帧, 帧], items: [...], ev: [...]}` ← 主力 |
| `pong` | `{c}` 原样回传 |

## 4. `state` 包长什么样

```jsonc
{
  "t": "state",
  "f": [                              // framesPerPacket 帧，时间戳严格递增
    {
      "st": 123.45,                   // 服务器模拟时间（秒），插值的唯一时间基准
      "snakes": [
        {
          "id": 7, "n": "贪吃蛇1号", "sk": "aurora", "ai": 0,
          "tr": 2,                    // 奖杯
          "d": 1.571,                 // 朝向弧度（画地面箭头 + 头对头判定的展示）
          "iv": 0,                    // 出生保护中
          "c": [0, 2, -1, 1],         // 颜色数组，-1 = 万能珠；长度即珠子数
          "b": [12.3, 45.6, 0,  11.5, 45.4, 0,  ...]   // 每颗珠 x,y,z 展平，2 位小数
        }
      ]
    },
    { "st": 123.467, "snakes": [ ... ] }
  ],
  "items": [[id, x, y, colorIndex], ...],   // 包级别，不随每帧重复
  "ev": [ {"t":"match", ...}, {"t":"death", ...} ]
}
```

三个设计点：

1. **一个包携带多帧**（`net.framesPerPacket`，现在是 2）。服务器 60Hz 模拟、30 包/秒发送。
   客户端只做内插不做外推，所以位置流必须稠密且连续——多帧打包让收包抖动不会造成"插值到空"。
2. **道具在包级别**。它们不会移动，只有被吃/刷新时才变，没必要跟着每帧重复。
3. **事件单独一条 `ev` 数组**。事件是"发生过一次"的东西（三消、撞击、死亡、夺杯、万能珠刷新），
   不参与插值，客户端收到就立刻放特效/音效/公告。三消事件里带着**被消掉那几颗珠的世界坐标**，
   客户端拿它生成会闪烁的"虚拟珠"——真实的珠子在服务器上是瞬间消失的。

## 5. 为什么没有序号、ACK、重传

WebSocket 跑在 TCP 上，**有序可靠**，丢包和乱序由 TCP 处理掉了。代价是队头阻塞：
网络抖一下会攒一批包一起到。这正是客户端要留 `interpDelayMs`(80ms) 缓冲、
并且**用微调播放速率而不是直接拨表**来对时的原因（见 `docs/design.md` §7）。

局域网上这套很划算：省掉了整个可靠性层的复杂度，而 1~2ms 的 RTT 让"不做预测"的手感损失可以忽略。
公网上这个权衡会翻转，见下半部分。

## 6. 断线

不重连。`ws.on('close')` 直接把蛇从世界里移除；客户端弹回登录页要求刷新。
奖杯已经落盘（`database/players.json`），重进按 `IP::昵称` 找回。

# 二、扩展到公网的方案

局域网到公网不是"换个 IP"这么简单，下面按**必须做 → 应该做 → 按需做**排列。
每一项都写清楚"为什么现在的做法会塌"。

## 2.1 传输：wss + 反向代理（必须）

**为什么必须**：页面一旦用 https 提供，浏览器就禁止连 `ws://`（混合内容），只能 `wss://`。

推荐 Caddy，因为它自动签 Let's Encrypt 证书且默认正确转发 WebSocket 升级：

```caddyfile
snake.example.com {
    reverse_proxy localhost:3000
}
```

用 Nginx 的话要显式处理升级头，还有两个容易踩的坑：

```nginx
location / {
    proxy_pass http://127.0.0.1:3000;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_buffering off;          # 否则代理会攒包，把 30Hz 的流打成一阵一阵
    proxy_read_timeout 3600s;     # 默认 60s，长连接会被无故掐断
}
```

客户端那行 `location.protocol === 'https:' ? 'wss' : 'ws'` 已经写好了，不用改。

**还要加连接保活**：现在只有应用层 1Hz 的 ping，但没有服务端超时踢人。
公网上半开连接（对端掉线但 TCP 没断）会堆积，要用 `ws` 的 `ping()` + `pong` 事件，
30 秒没响应就 `terminate()`。

## 2.2 身份：IP 绑定在公网会塌（必须）

现在档案键是 `IP::昵称`。公网上这两头都不成立：

- **一个 IP 对应很多人**：运营商 CGNAT、公司/学校出口、同一个 WiFi 下的所有设备
- **一个人的 IP 会变**：4G 切 WiFi、DHCP 续约、移动网络换基站

改成**客户端持有的匿名 token**：

```
首次连接：服务器签发 token = uuid()，随 welcome 下发
客户端：localStorage 存起来，之后每次连接在 join 里带上
服务器：token -> {nickname, trophies} 的表；token 不认识就当新玩家
防伪造：token 里带 HMAC(uuid, SERVER_SECRET)，或者干脆只认服务端表里存在的 uuid
```

这样换网络、换 IP 都不丢奖杯，同一台机器开多个浏览器 profile 天然是不同玩家。
要真实身份（跨设备找回、防小号）就得上 OAuth（微信/GitHub/…），那是另一个量级的工作。

**顺带**：放在代理后面时，`req.socket.remoteAddress` 永远是 `127.0.0.1`。
真要记录真实 IP（限流、封禁用），得读 `X-Forwarded-For` **并且**只信任自己的代理，
不能无条件信任这个头（客户端可以伪造）。

## 2.3 带宽：必须做 AOI（必须）

这是当前架构最硬的墙。实测（`tests/stress.js`，100 条蛇）：

| 场景 | 单客户端下行 |
|---|---|
| 100 蛇 / 50×50 | 1.8 MB/s |
| 100 蛇 / 380×380 | 4.1 MB/s |

原因是**每个包把全场所有蛇的所有珠子发给每个人**。局域网上一个客户端跑得动，
但客户端数是乘法关系：20 个客户端就是 20~80 MB/s 出口，家用宽带上行直接爆掉。

**AOI（Area of Interest，兴趣区域）**——只发你看得见的：

```
每个客户端维护一个视野圆：半径 = 相机可见范围 × 1.2
  视野内的蛇：完整珠子坐标，30 包/秒（和现在一样）
  视野外的蛇：只发头部坐标 + 名字/奖杯/长度，3~5 Hz（喂小地图和排行榜就够了）
  进入/离开视野时发 enter/leave，客户端据此建/销 SnakeView
```

实现要点：

- **代价是每客户端一次序列化**，不能再像现在这样"stringify 一次广播给所有人"。
  20 个客户端 × 30 包/秒 = 600 次序列化/秒，但每次都小得多，净收益是正的。
- **视野查询用网格哈希**（把地图切成 `cellSize × cellSize` 的桶，蛇按珠子登记到桶里）。
  这套结构**顺便能给碰撞用**——现在碰撞是 O(蛇数² × 珠数) 的暴力两两判定，
  100 蛇时占单帧耗时的 60~66%，加了网格就能降到接近 O(n)。一次改动解决两个问题。
- 客户端的小地图现在直接吃全量 `snakes`，改成吃"低频名册"即可，逻辑基本不变。

预估：视野内典型 5~10 条蛇，下行降到 **40~80 KB/s 每客户端**，是现在的 1/30 左右。

## 2.4 编码：JSON → 二进制（应该做）

AOI 之后如果还想再压一档：

- 坐标用 **int16 量化**：地图 380 单位映射到 65536 档，精度 0.006 单位，远超需要。
  一颗珠从 `"123.45,67.89,0"`（约 14 字节）压到 5 字节（x/y 各 2 字节 + z 1 字节）。
- 颜色数组用 `Uint8Array`，`-1` 换成 `255` 表示万能珠。
- 静态字段（名字、皮肤）只在 enter 事件里发一次，不随每帧重复。

合起来还能再省 **60~70%**。改动集中在 `world.frame()` 和 `net.sample()` 两个函数，
`tests/interp.js` 直接驱动真实的 `net.js`，改完能立刻验证插值没坏。

## 2.5 延迟：要不要上客户端预测（应该做，但看 RTT）

现在是**纯内插、零预测**：按下 W 到看见蛇转向，要等 `RTT/2 + interpDelay(80ms) + 一帧`。
局域网 RTT 1ms，总延迟约 90ms，感觉不出来。公网 RTT 60~150ms，总延迟 150~250ms，**手感会明显发飘**。

按代价从低到高：

1. **自适应插值延迟**（半天）。现在 `interpDelayMs` 是写死的 80。改成统计最近 N 个包的到达抖动，
   取 `p95 抖动 + 一个包间隔`，网络好时自动降到 40ms。
2. **只预测自己的蛇**（2~3 天，收益最大）。蛇的运动是**确定性**的——只依赖
   `targetDir / sprint / dt`，而 `snake.step()` 这段代码本来就可以直接搬到浏览器里跑。做法：
   - 客户端给每个 `input` 编号，本地立刻应用并把输入存进环形缓冲
   - 服务器在 `state` 里回带"我处理到的最后一个输入序号"
   - 客户端拿权威位置，从那个序号之后**重放**尚未确认的输入，得到修正后的现在
   - 偏差小于阈值就用几帧平滑吸收，不要硬拽（硬拽比不预测还难受）
3. **服务器侧输入抖动缓冲**（1 天）。公网上输入包到达也是抖的，服务器攒一小段再按序应用，
   比来一个用一个稳。

**碰撞、断尾、三消这些强耦合判定绝对不能预测**——它们依赖别人的状态，本地猜错就要回滚，
回滚一条蛇的"断尾接管"是灾难。预测只做自己的移动，其余一律等服务器。这条边界要守住。

## 2.6 安全与滥用（必须做一部分）

服务器权威这一点已经挡掉了最主要的一类作弊：客户端发不出位置，改内存也没用。剩下的是滥用：

| 风险 | 现状 | 公网要做 |
|---|---|---|
| 连接洪水 | 无限制 | 单 IP 并发连接数上限 + 入场速率限制 |
| 消息洪水 | 无限制 | 每连接每秒消息数上限；`new WebSocketServer({ maxPayload: 4096 })` |
| 跨站 WebSocket 劫持 | 不校验 Origin | 校验 `Origin` 头在白名单内 |
| 昵称 | 已过滤长度与 HTML 敏感字符 | 加敏感词过滤 |
| 房间被塞满 | 无上限 | 在线人数上限，满了排队或开新房 |

## 2.7 持久化：JSON 文件换 SQLite（应该做）

现在 `database/players.json` 是**每 3 秒把整个表重写一遍**。几十个玩家没问题，
上千条记录时每次写几百 KB，而且进程被 kill 时最多丢 3 秒的数据。

换 `better-sqlite3`：单文件、同步 API（不用改成异步）、有事务、几万玩家毫无压力。
表结构就两列：`token TEXT PRIMARY KEY, nickname TEXT, trophies INTEGER, last_seen INTEGER`。

## 2.8 容量与分片（按需）

单进程单世界。压测显示 100 条蛇只用掉 60Hz 预算的 22%，**CPU 不是瓶颈，带宽才是**。
所以扩容的正确顺序是：先 AOI 把带宽压下来，压到出口带宽打不满为止；
再不够才谈多进程。

多进程的话：**一个进程一个房间**，世界状态全在内存、不跨进程共享，前面按房间号做粘性路由
（`/room/:id` → 固定实例）。跨房间的全局排行榜放 Redis 或同一个 SQLite。
千万别试图把一个世界拆到多个进程——蛇的碰撞是全局耦合的，拆了就得做跨进程同步，不值。

## 2.9 运维（按需）

- `/healthz` 健康检查
- 指标：单帧耗时 p99、在线人数、出口带宽、每秒事件数（前三个 `tests/stress.js` 已经在量了）
- 优雅关闭：收到 SIGTERM 时广播"服务器维护中"，`profiles.flush()` 后再退出

## 落地顺序

| 步骤 | 工作量 | 不做会怎样 |
|---|---|---|
| 1. wss + 反向代理 + trust proxy | 半天 | 浏览器根本连不上 |
| 2. token 身份替代 IP 绑定 | 半天 | 同 NAT 下的人互相串号、换网就丢奖杯 |
| 3. Origin 校验 + 连接/消息限流 | 半天 | 一个脚本就能打满服务器 |
| 4. **AOI** | 1~2 天 | 超过十几个客户端出口带宽就爆 |
| 5. 自适应插值延迟 | 半天 | 网络好的人也要吃固定 80ms |
| 6. 二进制编码 | 1 天 | 带宽还能再省 2/3，非必须 |
| 7. 客户端预测与和解 | 2~3 天 | RTT > 60ms 时手感发飘 |
| 8. SQLite | 半天 | 玩家上千后写盘抖动、崩溃丢档 |
| 9. 房间分片 | 按需 | 单房间人数到不了几百 |

**1~4 是公网可用的下限**，5~7 是手感和成本优化，8~9 是规模问题。
其中第 4 项（AOI + 网格哈希）顺带把碰撞判定也从 O(n²) 降下来，是投入产出比最高的一项。

# 三、跨境部署：大陆 ↔ 海外，客户端不翻墙能行吗

结论先说：

| 目标 | 能不能做到 | 代价 |
|---|---|---|
| 两边都**能连上**，客户端不装任何东西 | **能** | 大陆侧要 ICP 备案；海外机房对大陆的可达性不受你控制 |
| 两边都**玩得跟手** | **单点部署做不到**，必须分区 | 大陆一台 + 海外一台，各自一个世界 |

跨太平洋的物理下限就摆在那：光在光纤里跑一个来回，中美之间大约 **140ms**，加上路由绕行和排队，
实测 RTT 通常 150~250ms。这是物理常数，任何"加速"都只能逼近它，不能突破。
而这个游戏现在是纯内插零预测，总延迟 = `RTT/2 + 插值缓冲 80ms + 一帧`——200ms 的 RTT 会直接变成
300ms 以上的操作延迟，蛇会明显"跟不上手"。

## 3.1 服务器放在中国大陆

- **大陆客户端**：正常，延迟 10~50ms，体验和局域网接近。
- **海外客户端**：一般能连（出境方向通常不拦），但延迟 150~300ms，且国际链路晚高峰抖动大。
- **必须做 ICP 备案**：在大陆境内提供公网 Web 服务，域名要备案。阿里云/腾讯云等大陆机房会
  对未备案域名的 80/443 做拦截。这是合规要求，没有绕过的正当办法——直接用 IP + 非标端口
  不是可行方案，也不建议。备案本身对个人项目不难，但需要域名、实名和几周时间。

## 3.2 服务器放在美国机房

- **海外客户端**：正常。
- **大陆客户端**：这是不确定性最大的一环。普通境外 VPS 从大陆**通常能直连**，但：
  - 延迟高（美西 150~200ms，美东 250~350ms）
  - 晚高峰国际出口拥塞，丢包和抖动都很大，TCP 一丢包就队头阻塞，实时流会一卡一卡
  - 可达性**不由你控制**，也不保证长期稳定
- 所以"客户端无需翻墙"在这种部署下**通常成立但不能承诺**，而且即使连上了，
  这个游戏的操作手感也已经不可接受。

## 3.3 真正可行的做法：**分区部署**

游戏世界本来就是"单进程 + 内存状态"，天然按房间切分（见 §2.8）。所以正解是：

```
大陆区服务器（阿里云/腾讯云，已备案）  ← 大陆玩家
海外区服务器（AWS / GCP / Vultr）      ← 海外玩家
        两个独立世界，各自的排行榜
```

- 玩家进入时按来源就近分配（用 IP 归属地判断，或者干脆让玩家自己选"国服/国际服"）
- 两边跑同一份代码、同一份 `config/game.config.js`，只是各自独立的世界
- 想要跨区总榜，用一个共享的数据库（Redis / 云数据库）同步奖杯数就够了，
  这条链路不实时，几秒延迟无所谓

**这是所有实时对战游戏的标准做法**，不是妥协——原神、王者荣耀都是分区的。

## 3.4 如果一定要"一个世界、跨境同场"

那就得把跨境这段链路的质量买回来，都需要备案：

| 方案 | 做什么 | 能到什么程度 |
|---|---|---|
| 大陆云厂商的全站加速（阿里云 DCDN / 腾讯云 ECDN） | 大陆边缘节点接入，走优质回国专线回源到海外 | RTT 从 250ms 降到 **80~120ms** |
| 全球加速（阿里云 GA） | 给一个大陆可达的入口 IP，走骨干网回源 | 类似，稳定性更好 |
| AWS Global Accelerator | anycast 入口 | **大陆没有落地节点，对这个场景基本没用** |
| Cloudflare | 中国网络需与国内伙伴合作且要备案 | 门槛高，个人项目不现实 |

两个前置条件：

1. **必须先做 AOI + 二进制编码**（§2.3、§2.4）。这些加速产品按流量计费，
   而现在是持续 30 包/秒的流，100 蛇时单客户端 1~4 MB/s——一个玩家一小时就是几个 GB，
   账单会非常难看。压到 40~80 KB/s 之后才谈得上。
2. **必须先做客户端预测**（§2.5）。80~120ms 的 RTT 下，纯内插仍然发飘。

## 3.5 传输协议：跨境场景下 TCP 是短板

跨境链路的特征是**高延迟 + 突发丢包**。WebSocket 走 TCP，一丢包就队头阻塞——
后面已经到达的位置帧全被卡住，表现就是"卡一下然后瞬移一段"。

浏览器上有两个不需要客户端装任何东西的替代品：

- **WebTransport**（HTTP/3 over QUIC）：支持不可靠数据报，丢了就丢，下一帧照常到。
  位置流本来就是"最新的才有用"，丢一帧完全无所谓。Chrome/Edge 已支持，Safari 还在跟进。
- **WebRTC DataChannel**（`ordered:false, maxRetransmits:0`）：同样是不可靠模式，兼容性最好，
  但要自己搭信令，复杂度高一档。

对这个项目，跨境部署时值得把 `state` 下行换成 WebTransport 数据报，
上行的 `input`/`join` 这类必达消息仍然走可靠通道。改动集中在 `net.js` 和 `server/index.js` 的收发层，
`world.js` 和插值逻辑完全不用动。

## 3.6 落地建议

如果目标是"大陆和海外的朋友都能玩"：

1. **先做分区**（§3.3）。一台大陆机 + 一台海外机，各自一个世界。成本最低、体验最好、没有技术风险。
2. 大陆那台把备案办了；海外那台随便找家 VPS。
3. 真需要跨区同场，再按 §3.4 上加速，但**先把 AOI 和客户端预测做完**，否则花了钱也玩不好。

如果目标是"一台服务器服务全球"——**不建议**。物理延迟决定了这不是工程问题，
花再多钱也只能把 250ms 压到 100ms，而 100ms 对这种贴身碰撞的玩法仍然是明显的劣势。
